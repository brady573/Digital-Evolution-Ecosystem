# A3.4 canonical restore state — design specification

Status: **Owner-accepted and implemented.** All six implementation tasks are complete. The ordering below is structural in code, not aspirational: `restore` obtains canonical state only through `validateCanonicalRestoreState`, and the candidate/validated distinction is enforced by the compiler via `@ts-expect-error` directives in `packages/sim-runtime/src/canonical-restore-type-boundary.ts`, which `pnpm typecheck` compiles.

Baseline: `c7e84ab` (A3.3 merged to main). Design basis: `tranche-a-decisions.md` Decision 2 and the standing rules on absence-vs-validity, absorber classification, and generated artifacts.

## Acceptance statement

> A source checkpoint that passes A3.3 preflight is transformed by explicit historically justified rules into one canonical restore representation; that representation must satisfy the current non-simulation restore contract before any restored state becomes live.

## Scope, stated honestly

This is **not** full-checkpoint canonicalisation. `experiment` and `control` deliberately remain under sim-core's existing checkpoint semantics, with the live-step guards that A3.3 named and left untouched. A3.4 canonicalises the analysis, control-analysis and decisions layers only, and validates only those. Any naming in this unit must not imply otherwise — that was the point of the A3.3 lesson about names that describe a capability the code lacks.

## Ordering

```
raw payload
  → validateCheckpoint            A3.3 source-schema preflight, unchanged
  → engine-version guard          pre-existing, unchanged
  → canonicalizeRestoreState      new, pure → CanonicalRestoreCandidate
  → validateCanonicalRestoreState new → ValidatedCanonicalRestoreState
  → decode + assign               restore, consuming only the validated form
```

A3.3's preflight remains solely responsible for source-schema admissibility: which absences are historically valid, and whether every present value is valid at its declared schema. A3.4 begins only after that has passed.

### Candidate versus validated — the type boundary is the point

Canonicalisation and validation are separate stages with separate types, and they must not collapse into one.

`CanonicalRestoreCandidate` is what migration produces. It may already carry the fully materialised canonical *shape*, but every nested value in it is **runtime-untrusted**: no migration rule has been checked against the current contract yet. `ValidatedCanonicalRestoreState` is what only `validateCanonicalRestoreState` can produce.

This exists because the entire purpose of the validator is to catch the case where a historically justified rule produces something the current contract rejects. If canonicalisation returned a trusted type, the type system would be asserting that conclusion before the runtime ever tested it — the same failure A3.3 corrected in prose, moved into the type layer.

`restore` consumes `ValidatedCanonicalRestoreState`. It may not consume a candidate, and it may not widen one itself.

## Dependency neutrality

`packages/contracts` is depended on by sim-analysis, sim-runtime and the rest of the product, so it must not import observer constructors from sim-analysis or policy constants from sim-decisions, and no package dependency is reversed to achieve this.

`canonicalizeRestoreState` therefore lives in contracts and takes an explicit, immutable context supplied by sim-runtime:

```ts
export interface CanonicalizationContext {
  /** Running-build generator versions. Never read from the save. */
  readonly policyVersion: string;
  readonly catalystPolicyVersion: string;
  /**
   * The running build's current checkpoint schema, supplied rather than
   * hardcoded: contracts must not import sim-core, and canonical validation
   * holds the result to *this* contract.
   */
  readonly currentSchema: CheckpointSchemaVersion;
  /**
   * The observer's own initial detector state, supplied by the caller because
   * contracts cannot construct an observer. Only the keys A3.3 named rules for.
   */
  readonly detectorDefaults: Readonly<Record<"dep" | "niche", unknown>>;
}
```

sim-runtime builds it once from `DECISION_POLICY_VERSION`, `CATALYST_POLICY_VERSION`, and the declared initial state of a freshly constructed observer. The truth about what an empty detector looks like stays in sim-analysis; contracts only carries the values it was given.

Context properties, all normative:

- **Supplied by trusted running code, never by checkpoint contents.** No field of the context may be derived from, defaulted from, or overridden by the payload being canonicalised. A save that could influence its own migration would make migration a bypass.
- **Immutable for one canonicalisation call.** Canonicalisation must not write to the context, and must not assume it may be re-read and mutated between stages.
- **Obtaining the context consumes no RNG and mutates no simulation or analysis state.** Building it must be observably free of side effects, or every canonicalised restore would perturb replay.
- **Policy versions come from their owning running modules** — `DECISION_POLICY_VERSION` from sim-decisions, `CATALYST_POLICY_VERSION` from sim-decisions, not from a saved value.
- **Analysis defaults come from sim-analysis authority and are passed as values.** The meaning of "an empty detector" is owned there; contracts never re-derives it.
- **Canonicalisation mutates neither the source payload nor the supplied defaults or context.** Values are copied on the way in and on the way out.

## Types

```ts
/**
 * What canonicalisation produced. Deliberately narrower than a checkpoint: the
 * encoded simulation is NOT canonicalised here, and every nested value is still
 * runtime-untrusted until validateCanonicalRestoreState has run.
 */
export interface CanonicalRestoreCandidate {
  readonly analysis: unknown;
  readonly controlAnalysis: unknown | null;
  readonly decisions: unknown;
}

/**
 * A candidate that satisfied the current non-simulation restore contract.
 * Only the validator can produce this type.
 */
export interface ValidatedCanonicalRestoreState {
  readonly analysis: unknown;
  readonly controlAnalysis: unknown | null;
  readonly decisions: DecisionCheckpoint;
}
```

`validateCanonicalCheckpoint` is rejected as a name: it would imply the simulation was canonicalised and revalidated. `canonicalizeRestoreState` returns a **candidate**, not a state.

`validateCanonicalRestoreState` is a narrowing boundary: it returns a `ValidatedCanonicalRestoreState` or throws `CheckpointRejectionError`. Callers receive the narrowed type and cannot bypass the check by ignoring a return value.

## Canonicalisation

Pure, non-mutating, and idempotent: the source payload is never written to, neither the supplied context nor the defaults are written to, and every returned object is freshly constructed.

- **Entity references.** Existing `migrateEntityRefs`, value-deduplicated on `(kind, id)`.
- **Detector sub-states.** `dep` and `niche` filled from `context.detectorDefaults` when absent, at every schema, for both the live and matched-control observers. A detector that has not fired genuinely has no sub-state; this is the same meaning as before, produced explicitly.
- **Pending decision.** `source` backfilled for a 0.2 pending carrying a `sourceEventId`; `contextSnapshot` set to `null` for 0.2. A 0.1 payload has no decisions container, so an empty decision history is synthesised — documented as running-build state, never as a historical value.
- **Resolutions.** `offerTick` from the resolution's own tick and `catalystId` null for 0.2; `choiceTitle` and `directEffectDescription` set to the explicit unrecorded marker for 0.2.
- **Pacing.** A 0.3 payload keeps its own `lastDecisionTick` and `lastMajorCatalystTick`; a 0.2 payload reconstructs the decision tick from its own records and reads the cooldown as `null`; 0.1 starts at 0 and `null`.
- **Generator versions.** Always the running build's, at every schema.

## Validation, and one definition of "valid"

The low-level value validators are factored out of `validateCheckpoint` and shared by both call sites. There must never be a second, independently evolving definition of what a valid value is.

- Preflight calls them with the payload's declared source schema, tolerating only the absences that schema's rules name.
- Canonical validation calls them with the current contract, requiring every key a current save writes.

`validateCanonicalRestoreState` therefore fails when a rule's canonical default is something the current contract would reject — which is the standing rule made enforceable: a rule and a validator in disagreement stops being a silent disagreement.

## Idempotence property

Canonicalising an already-canonical payload must not change its meaning and must not apply a second migration effect. Asserted behaviourally: canonicalise, validate, feed the result back as a source, canonicalise again, and require the second result to equal the first in decisions, analysis and control-analysis, with reference counts and pacing values unchanged. This is what makes the representation safe to re-enter and to re-save.

The specific hazard is **re-derivation**: a backfill that computes its value from another field will compute it again on a second pass, and a value that happens to be stable once can silently change twice. A marker assigned with `??` is stable by construction; a derived value is not. The property test is what catches the difference.

## Equivalence evidence — three tiers, and what each one is

The A3.3 lesson was that relabelling a current save can manufacture a historical save that no supported build ever wrote. Tier 1 is kept because it is a genuinely useful control, and is named as a control rather than dressed as history.

**Tier 1 — preservation control. Not historical evidence.** A real current save relabelled `0.3`, whose writer emitted a compatible shape for every field a current save carries. `restore(current)` and `restore(relabelled)` must produce identical runtime state and identical re-saved checkpoints. What it proves is that the 0.3 branch is not a bypass. What it does *not* prove is anything about what 0.3 builds actually wrote.

**Tier 2 — writer-shaped 0.3 fixtures.** Two variants, each reconstructed from the writer that produced it:
- *early 0.3*, as `b040b19` wrote it: no `pc`, no `to`/`cu`, no `lineageInterval`/`lastLineageFlows`, no `dep`/`niche`, bare-number entity references.
- *late 0.3*, 0.3 plus `3ddb287`, `4da996c`, `af9ad23` and `afbccfc`: all of those present, tagged references.

For each: restore succeeds, the restored world matches the restore semantics A3.3 already accepted, and re-saving produces the current schema.

**Tier 3 — bounded 0.1 and 0.2 fixtures.** The genuinely shaped ones: 0.2 carries a pending with no `source` or `contextSnapshot` and resolutions with no `offerTick`, `catalystId`, `choiceTitle` or `directEffectDescription`, and no pacing fields; 0.1 has no decisions container. Equivalence is asserted only over what each schema could carry, and the bound is written into the assertion message rather than left implied — a 0.2 world can never equal a current world byte for byte, and a test that pretended otherwise would be a fake proof.

## Absorber ownership

`dep`/`niche` absorption moves from `constructor-default` to the canonical migration, for all four rules (`analysis.dep`, `analysis.niche`, `controlAnalysis.dep`, `controlAnalysis.niche`). The observer's constructor default may remain as an implementation fallback, but it is no longer the declared compatibility mechanism, because a preflighted payload always reaches the migration first.

What changes: `absorber`, the `omission` prose describing *how* the value is supplied, and the A3.3 rule-table probes, which re-point from the sim-analysis constructor to the canonicalizer.

What does **not** change: the 18 historical rules, their `appliesToSchemas`, their `historicalBasis` evidence, and their hazard classifications. Those stay unless implementing this architecture produces actual evidence that one is wrong.

## Out of scope

No sim-core biological behaviour changes. No change to the live-step guards. No change to A3.3's preflight, its boundary artifact, or the six rejection conditions. No new dependency, network surface, or export.

## Risks

- **Two absorbers for one omission.** If migration fills `dep` and the constructor also does, the declared mechanism is ambiguous again. Mitigation: migration is authoritative for any preflighted payload; the constructor default is unreachable on that path.
- **Validation drift.** Two definitions of "valid" would let the boundary lie in two places. Mitigation: shared validators, asserted by the fact that both call sites compile against the same functions.
- **Over-strictness on the historical path.** Canonical validation is new strictness applied to legacy saves, and this repository's documented failure mode is rejecting too much — which presents as user-visible load failures, not test failures. Mitigation: tiers 2 and 3 are the acceptance evidence, and they assert that historical worlds still open.
- **Idempotence broken by a non-idempotent default.** A marker assigned with `??` is stable, but a backfill that derives from another field would re-derive on a second pass. The property test is the guard.
- **The type boundary eroding.** If `canonicalizeRestoreState`'s return type is later widened, or `restore` is changed to accept a candidate, the compiler stops enforcing the check and the validator becomes advisory. The narrowing return type is the guard, and its value is that removing the check becomes a type error rather than a silent weakening.

## Validation

Per handoff §8, required green: `test:migration`, `test:flows`, `test:dependency:arc`, `test:niche`, `test:decisions`, `test:time-controls`, `typecheck`, `test:validation-arch`, plus `pnpm validation:check` after any manifest edit. `quick` is the shard that surfaces a problem in the migration table.

Evidence is completed by a manifest-routed CI run on the frozen candidate. Local runs are authoring-time signal only; the phone is not where long evidence is waited for.
