# A3.4 Canonical Restore State Implementation Plan

**Delivery status: all six tasks complete.** Every step below is checked. The
checklist records the plan as accepted; where the delivered implementation
deliberately diverged from the plan's letter, the divergence is recorded under
*Deviations from this plan* rather than left for a reader to discover.


> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking.

**Goal:** Make `source → canonical migration → canonical validation → restore` structurally true, so a migrated historical save is held to the current non-simulation restore contract before any state becomes live.

**Architecture:** A pure `canonicalizeRestoreState` in `packages/contracts` returns a runtime-untrusted `CanonicalRestoreCandidate`; `validateCanonicalRestoreState` is a narrowing boundary returning `ValidatedCanonicalRestoreState`; `restore` consumes only the validated form. Both preflight and canonical validation call the same extracted low-level validators.

**Tech Stack:** TypeScript (strict), pnpm, tsx, Node `assert/strict`, manifest-routed validation.

**Spec:** `docs/architecture/A3.4-CANONICAL-RESTORE.md`

## Global Constraints

- `packages/contracts` must not import from sim-analysis, sim-decisions or sim-core. No package dependency is reversed. sim-runtime supplies all running-build values through `CanonicalizationContext`.
- `experiment` and `control` are NOT canonicalised. They stay under sim-core's checkpoint contract. No sim-core biological behaviour changes; the live-step guards in `engine.ts` are untouched.
- The 18 migration rules, their `appliesToSchemas`, `historicalBasis` and `hazard` values stay unchanged unless implementation produces actual evidence one is wrong. Only `absorber` and `omission` prose for the four dep/niche rules change.
- A3.3's `validateCheckpoint` preflight stays first and unchanged in behaviour.
- Canonicalisation is pure, non-mutating, and idempotent. It must not re-derive a backfilled value on a second pass.
- One definition of "valid": preflight and canonical validation share the same low-level validators.
- `restore` may not accept a `CanonicalRestoreCandidate`.
- Do not commit, push or open a PR without separate authorization.

## Review Focus

- A rule whose canonical default the current contract rejects — the validator must catch it rather than let it load. Pinned in Task 4.
- A migration value that re-derives on a second canonicalisation pass. Pinned in Task 2's idempotence test.
- A canonical result that omits something the current writer always emits (e.g. a 0.1 world reaching restore without a decisions container). Pinned in Task 2.
- A historical save that stops opening because canonical validation is stricter than the source contract. Pinned in Task 5 tiers 2 and 3.
- A `restore` change that widens the validated type or re-accepts a candidate, silently making the validator advisory. Pinned in Task 6 as a type-level test.

## Deviations from this plan

Each of these was a deliberate, reported decision rather than an oversight.

1. **Task 5's "rewrite `restore`" was already delivered by Task 3.** `restore`
   consumes one validated canonical state with no per-schema branch from the
   start; Task 5 therefore contributed only the three tiers of equivalence
   evidence. The plan's ordering here was already satisfied.
2. **The type-barrier guard is under a package `src/`, not the boundary suite.**
   The plan's own example put it in `tools/validation/`, but no tsconfig compiles
   `tools/`, so a `@ts-expect-error` there would be checked by nothing and could
   not protect the repository after merge. It lives in
   `packages/sim-runtime/src/canonical-restore-type-boundary.ts`, which
   `pnpm typecheck` compiles.
3. **The guard does not use `as any`.** The plan's example cast the candidate
   before passing it, which would have erased the very distinction under test. The
   delivered guard asserts both sides directly — the candidate cannot be consumed
   where a validated state is required, and the validated state can — with no
   cast anywhere.
4. **Tier 1 compares runtime state and the re-saved checkpoint**, not analysis
   alone as the plan drafted it. An analysis-only comparison passes while the
   simulation layer diverges, which is the wider risk. Only `worldId` is excluded,
   by name, because it is presentation identity minted per restore.
5. **Tier 3 compares named surviving dimensions** rather than asserting a finite
   tick, which the Owner rejected as insufficient. Each schema's surviving
   dimensions are compared and its unrepresentable fields are named as excluded.
6. **`EcologyObserver.restore` moved from `any` to `Record<string, unknown>`.**
   The `any` was the escape hatch that let an unvalidated value through, so the
   barrier could not be compile-enforced until it was removed. Type-only; no
   behaviour change. This touches `sim-analysis`, which the plan did not list.
7. **Review repairs beyond the plan's scope.** Two independent reviews found four
   regressions introduced by this unit and four assertions that passed without
   testing anything. All were repaired and are proven by mutations that break
   each one and only it.
